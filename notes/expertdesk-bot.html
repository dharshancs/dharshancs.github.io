/system-notes/expertdesk-monitor

Context: Spotted a workflow on an expert Q&A platform (name not disclosed per usage agreement) that required manual page refresh every 10-15 seconds to catch incoming questions before other users. Built an automation system. It broke five times at new scale ceilings. Each break forced a better architecture. Ran this as a paid service before open sourcing.

The Problem

  • Manual refresh loop — 10-15 seconds, eyes on screen, no breaks
  • First to refresh after a question posts wins the assignment
  • Not solvable with a simple timer — needed a real authenticated browser session

v1 — Selenium + Telegram

  • Selenium handles login and page refresh loop in a headless Chrome window
  • Telegram Bot API fires a notification the moment the question button is detected
  • No more screen monitoring. Worked for a single account.

v2 — Multiprocessing: One Process Per Account

  • Demand grew. Multiple accounts needed to run simultaneously.
  • Used Python multiprocessing — each OS process gets its own Chrome instance and its own cookies
  • Stable at 5-6 accounts. At 10-15, Chrome's per-process memory overhead (~200MB each) caused OOM crashes.

v3 — Pyppeteer: Shared Browser, Isolated Contexts

  • Replaced Selenium + multiprocessing with Pyppeteer + asyncio
  • One Chrome process hosting multiple isolated incognito contexts — one per account
  • Contexts share one Chrome process but have completely separate cookies and sessions
  • Memory ceiling extended. But Pyppeteer leaked memory over hours — needed process restarts every few hours.

v4 — Playwright + OTP Handling

  • Replaced Pyppeteer with Playwright — actively maintained, no memory leak
  • Platform started enforcing two-factor authentication on some accounts
  • Bot now detects the OTP screen, sends a Telegram message to the account owner asking for the code, polls for their reply, cleans the text, and types it character-by-character (required because React's field validators need individual keystroke events)
  • Persistent contexts still accumulate memory over long runtimes — architectural problem, not a library problem

v5 — Cookie Rotation Architecture

  • Key insight: the 20-second wait between page reloads is dead time — a browser context sitting idle during that window burns ~100MB doing nothing
  • After login, session cookies and storage state saved to disk per account. Context closed immediately.
  • To check for a question: load cookies from disk → open fresh context → navigate → check → close context
  • Contexts live for a fixed cycle duration (1 hour), then destroyed and recreated from refreshed cookies
  • Dead cookie detection: if saved session redirects to login, auto re-login runs and fresh cookies are written to disk. No human intervention.
  • During the cooldown gap between cycles, no context exists for that account — zero memory held.

Result

  • 150 concurrent accounts on a single server instance
  • Memory stays flat regardless of runtime — no more restarts
  • 24/7 uninterrupted operation with automatic session recovery
  • Ran as a paid service before open sourcing the full codebase

What This Taught Me

  • Idle time in one context is wasted memory — short-lived contexts scale; persistent ones don't
  • Real scaling problems only appear under real load — every version felt fine until it didn't
  • Library choice matters for long-running processes — a memory leak that's invisible in testing becomes critical in production
  • OTP handling at scale forced understanding of how JS field validators work at the keystroke level
