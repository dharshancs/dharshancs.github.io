/system-notes/chegg-automation

Context: Spotted a workflow requiring manual page refresh every 10-15 seconds to catch incoming questions before other users. Built an automation system. It broke five times at new scale ceilings. Each break forced a better architecture.

The Problem

  • Manual refresh loop — 10-15 seconds, eyes on screen, no breaks
  • First to refresh after a question posted wins the assignment
  • Not automatable with a simple timer — needed real browser session

v1 — Selenium + Telegram

  • Selenium handles login and page refresh loop
  • Telegram API fires notification the moment a question is detected
  • No more screen monitoring. Worked for a single user.

v2 — Multi-user: Separate VMs

  • Demand grew. Others wanted access.
  • Deployed same unmodified script on individual AWS EC2 instances
  • One VM per user — worked, but per-user cloud cost was unsustainable

v3 — Single Instance, Parallel Processes

  • Consolidated to one EC2. One file per user running as parallel processes.
  • Stable at 5-6 users. At 10-15 accounts, Selenium's per-browser memory overhead caused OOM crashes.

v4 — Pyppeteer Migration

  • Replaced Selenium with Pyppeteer — headless Chromium, lighter footprint
  • Ceiling moved from ~15 to ~20 accounts
  • Root problem unchanged: one live browser context per account, always idle during wait period

v5 — Cookie Rotation Architecture

  • Key insight: the 10-15 second wait between refreshes is dead time — a browser context sitting idle burns memory for nothing
  • On startup: each account logs in once, session cookie saved to disk
  • Single event loop: load cookie → check for question → alert if found → drop cookie → load next account's cookie
  • Idle wait time reused as account-switching time across all 150 accounts
  • Cookie validation failure triggers auto re-login, fresh cookie saved, loop continues
  • No persistent browser contexts. No memory blowup.

Result

  • 150 concurrent accounts on a single EC2 instance
  • 24/7 uninterrupted operation with automatic session recovery
  • Zero human intervention required post-deployment

What This Taught Me

  • Stateless session management scales; stateful browser contexts do not
  • Idle time in one context is productive time in another — concurrency through time-slicing
  • Real scaling problems reveal themselves only under real load — design for the ceiling you haven't hit yet
