/origin_story

I saw a broken process.
So I automated it.
Then I scaled it to 150 accounts.

This is the story of a system built through five iterations — each one breaking at a new scale ceiling, each one forcing a smarter architecture.

v1
the spark
Selenium + Telegram API

Spotted a process that required manual intervention every 10-15 seconds. Built a scraper that automated the loop and pushed Telegram alerts the moment an event triggered. First version. It worked.

Selenium Telegram API Python
v2
demand
Multi-user on Separate VMs

Others wanted access. Deployed the same unmodified script on individual AWS EC2 instances — one VM per user. Horizontal scaling by duplication. It worked but cost per user was high.

AWS EC2 Multi-VM
v3
first wall
Single Instance, Parallel Processes

Consolidated to one EC2 instance, running one process per user in parallel. Cost dropped significantly. Stable at 5-6 users. At 10-15 accounts, memory pressure from Selenium's per-browser overhead started crashing the system.

Multiprocessing Single EC2 ⚠ OOM at 15 accounts
v4
second wall
Pyppeteer Migration

Replaced Selenium with Pyppeteer — headless Chromium with a smaller footprint. Extended the ceiling to ~20 accounts. But the core architecture still required one live browser context per account. Same fundamental constraint, slightly higher limit.

Pyppeteer Headless Chromium ⚠ fails at 20+
FINAL ARCHITECTURE
v5
the solve
Cookie Rotation Architecture

The key insight: the 10-15 second wait between refreshes is dead time. A browser instance sitting idle burns memory for nothing. Eliminated the need for persistent browser contexts entirely.

01 — each account logs in once, saves session cookie to disk
02 — single loop: load cookie → check → alert if hit → drop cookie → next account
03 — idle wait time reused as switch time across all 150 accounts
04 — cookie validation failure triggers auto re-login and cookie refresh
150
accounts handled in
a single instance with zero memory blowup
Cookie Pooling Session Management Auto-recovery AWS
WHAT THIS TAUGHT ME

Every version broke at a new ceiling. Every break forced a better mental model. By v5 I wasn't just fixing bugs — I was rethinking the concurrency model from scratch. That's what real scaling looks like.
